## Layout

| Path | What it is |
| --- | --- |
| `portal/` | The portal: `index.html`, `catalogue.js` (the one file that says what texts it reads), `parallels.js` (links the class made), `data/` (the texts). The whole seminar's tool. |
| `tools/` | `import_text.py` (plain text → data file), `check_data.py` (checks data files). |
| `sources/` | The source transcriptions the data files are generated from. Put them here. |
| `method-log/` | The Method Log page and the sessions committed to the repository. |
| `Individuals/<name>/` | A participant's own sandbox. Belongs to its owner. |
| `docs/` | The method and how-tos. |
| `.github/` | `CODEOWNERS`, issue forms, the pull-request template. |

## Architecture: plain HTML and scripts, plus generated data

- Each app is **an `.html` file**: markup, a `<style>` block and a `<script>` block, with its
  texts in `.js` files beside it.
- **No build step, no framework, no dependencies** (fonts from the system), **no server**.
  State is in module-scope variables, or in the browser's `localStorage` where a page says so.
- Texts are loaded with plain `<script src>` tags, not `fetch()`, so the apps open from
  `file://`. A data file is `const NAME = <JSON>;`, and the JSON must stay valid.
- The portal exposes one global, `window.PORTAL` (`S`, `P`, `TEXTS`, `ALL`, `runQuery`,
  `parseQuery`, `norm`, `tokens`, `openPassage`, `addToHandout`). Tools beside the portal read
  it through that and never edit the portal.

## Rules

- **Generated data is never hand-edited.** Files in `portal/data/` that begin "Generated by
  tools/import_text.py" are regenerated from `sources/`. Correct the source or the importer's
  options and run it again.
- **A passage's `id` and a text's `key` never change** once anything links to them
  (`#p=key:id`, handouts, parallels).
- **Say how accurate a text is.** Any OCR or machine-made text carries `accuracy` in its
  catalogue entry. Never present a machine reading as a clean one.
- **Label machine output** (OCR, machine translation, "found by machine") wherever it appears.
- **Change only what was asked.** A change inside a participant's folder stays in it. A
  change to the portal that is not asked for does not belong in a request to build a tool.
- **Do not invent text, citations or translations.** If one is missing, say so or leave an
  obvious placeholder.
- **Keep the pages readable.** Plain DOM, short functions, comments that say why.

## Checking a change

There are no tests. Verification is visual:

1. `python3 tools/check_data.py` if a data file changed.
2. Syntax-check what you touched with whatever JavaScript engine exists on the machine
   (`node --check file.js`, or `gjs`, or `osascript -l JavaScript` on macOS). To check an
   app's inline `<script>`, extract it first and **strip HTML comments** (script tags in
   explanatory comments produce fake errors).
3. Open the page: double-click it, or `python3 -m http.server` at the repository root, then
   click through the change and look at the browser console for red errors.
   Headless Chrome, where installed, renders without a display:
   `google-chrome --headless=new --virtual-time-budget=5000 --screenshot=out.png file:///abs/path.html`
4. The portal's **About** page reports every file that failed to load and every link that
   points nowhere.

A pull request says which of these were done and which were not.

## Git

- Work on a branch; never push to `main` directly.
- One change per pull request; a description that says what changed, how to try it, and the
  preview link (`https://raw.githack.com/OWNER/REPO/<commit-id>/portal/index.html`).
- After a push, give the preview link.
